커널 안의 가상머신

챕터 전환 — "커널 안의 가상머신이라는 말, 이상하지 않습니까?"로 물음표를 심어두면 8장(VM의 실체)에서 회수된다.
The problem

커널 확장의 두 가지 길

커널에 코드를 넣는 전통적 방법은 커널 모듈 — 강력하지만 커널과 운명을 함께합니다.

커널 모듈 (LKM · Loadable Kernel Module)

  • 버그 하나 = 커널 패닉, 시스템 전체 다운
  • 커널 버전마다 재컴파일·재검증 — ABI(Application Binary Interface) 비보장
  • 서명·배포·감사 부담, 보안팀의 승인 장벽
  • 메모리 접근 무제한 — 격리 장치 없음

eBPF 프로그램

  • Verifier가 로드 전에 안전성을 증명 — 크래시 불가
  • 레지스터 기반 샌드박스 VM에서 실행, JIT(Just-In-Time) 컴파일로 네이티브 성능
  • CO-RE(Compile Once – Run Everywhere)로 커널 버전 간 이식 — 재컴파일 없음
  • 재부팅·모듈 로드 없이 즉시 attach / detach
계측도 같은 딜레마 — ptrace·strace는 이벤트마다 대상 정지 + 컨텍스트 스위칭 왕복, 프로덕션에선 감당 불가 "안전하게 커널을 프로그래밍한다" — 이 설계의 원형은 30년 전에 이미 있었다
커널 모듈의 공포부터 — 버그 하나 = 커널 패닉, 보안팀이 왜 모듈을 싫어하는지 경험담이 있으면 여기서. ptrace/strace 칩은 계측 쪽도 같은 딜레마라는 보조 논거. 브릿지: "이 문제의 답은 30년 전에 있었다".
Prior art — 1992

해답의 원형 — tcpdump의 패킷 필터

tcpdump는 필터를 유저스페이스에서 돌리지 않습니다 — 표현식을 바이트코드로 컴파일해 커널 안으로 내려보내고, 매치된 패킷만 돌려받습니다.

eBPF가 물려받은 세 가지

  • 코드를 데이터가 있는 곳으로 — 패킷 전체를 복사해 거르지 않고, 필터를 커널에 주입
  • 검증 가능한 제한 명령어 — 임의 기계어가 아닌 바이트코드
  • 커널 수정 없는 프로그래밍 — 커널 내 엔진이 실행
  • eBPF는 이 원리를 그대로 두고 엔진만 재설계 — 'e'는 extended
cBPF(classic Berkeley Packet Filter) — 레지스터 2개 · 32-bit · 소켓 전용 → eBPF(extended BPF) — 11개 · 64-bit · 커널 전역 지금도 tcpdump 필터는 커널에서 eBPF로 변환되어 실행된다
tcpdump는 다들 쓴다 — port 443 필터가 유저스페이스가 아니라 커널 안에서 돈다는 게 반전 포인트. 물려받은 세 가지(코드를 데이터로 · 검증 가능한 바이트코드 · 커널 무수정)를 또박또박. e = extended.
Evolution — 1992 to today

패킷 필터에서 범용 커널 VM까지

도입 배경: 커널 기능 하나가 메인라인을 거쳐 배포판에 닿기까지 수년 — 컨테이너 시대의 네트워킹·관측·보안 요구를 커널 릴리스 주기가 따라가지 못했습니다.

커널 릴리스 주기 ≫ 인프라 요구의 변화 속도 모듈은 위험하고, 커널 포크는 유지비용이 크다 선행 기술 DTrace는 CDDL 라이선스 — GPL 커널에 통합 불가, 독자 노선을 강제한 배경 해법 — 커널 안에 안전한 프로그래밍 계층을 내장한다
타임라인은 왼쪽부터 순서대로 — 2014 커널 3.18이 진짜 탄생(bpf() 시스템 콜 + Maps). DTrace CDDL 칩은 꼭 언급: 라이선스가 기술 노선을 강제한 사례로, 35장 NFM에서 현대판이 다시 나온다.
The concept

기술 컨셉 — 커널 이벤트에 반응하는 이벤트 구동 프로그램

① 이벤트 구동 — 데몬이 아니라 커널 이벤트에 반응하는 코드 조각 ② 샌드박스 — Verifier가 증명한 프로그램만 실행 ③ 공유 상태 — 데이터 교환은 모두 Maps 경유
핵심 문장: eBPF 프로그램은 데몬이 아니라 이벤트에 반응하는 코드 조각. 그림의 ①트리거 ②샌드박스 ③Maps 경유 소통 세 가지가 챕터 1 전체의 목차이기도 하다.
"Virtual machine"?

'가상머신'의 실체 — JVM처럼, VMware가 아니라

eBPF VM은 하드웨어 가상화가 아니라 커널이 정의한 명령어 실행 모델입니다 — 바이트코드라는 중간 표현이 있어야 Verifier가 정적 분석을 할 수 있습니다.

구분하드웨어 VM — KVM · VMwareeBPF VM
가상화 대상CPU · 메모리 · 디바이스 전체명령어 세트 규격 — 레지스터 11개 · 64-bit · 스택 512 B
존재 이유OS 단위 격리검증 가능한 중간 표현 + 아키텍처 독립 (x86 · ARM · RISC-V)
실행 방식하이퍼바이저 경유JIT 컴파일 → 네이티브 기계어로 커널에 상주
런타임 오버헤드상시 존재사실상 0 — 커널 함수 호출과 동일 비용, 인터프리터 없음
VM이라 부를 수 있는 4가지 근거 ① 전용 바이트코드 + 레지스터 11개 실행 레이어 ② JIT 내장 — 가상 명령어를 네이티브 기계어로 ③ Verifier — 실행 전 안전을 증명하는 샌드박스 ④ 소통 창구는 Maps · Helper/KFunc뿐 — 임의 커널 메모리 접근 차단
실제 비용은 로드 타임 1회 — Verifier 검증 + JIT 컴파일 런타임 제약은 속도가 아니라 표현력 — 512 B 스택 · 명령어 한도는 증명의 대가
JVM 비유가 가장 잘 통한다 — VMware가 아니라 바이트코드 실행 규격. 표보다 아래 칩의 "VM이라 부를 수 있는 4가지 근거"가 핵심 메시지. 런타임 비용은 사실상 0, 실제 비용은 로드 타임 1회.

From C to kernel

소스에서 커널까지 — 실행 파이프라인

레지스터 11개 · R0–R10 R10 = 읽기 전용 프레임 포인터 스택 512 B Verifier를 통과해야만 실행
흐름을 손으로 따라가며 — 소스 → Clang → .o → bpf() → Verifier 관문 → JIT → attach. 빨간 점선(로드 거부)을 꼭 짚을 것: 검증 실패 프로그램은 커널에 발도 못 들인다. 다음 장이 그 관문의 내부.
The gatekeeper

Verifier — 실행 전에 안전을 증명한다

런타임 격리가 아니라 로드 타임 정적 검증. 증명에 실패하면 커널은 프로그램을 받지 않습니다.

무엇을 검사하는가

  • CFG(Control Flow Graph) 전수 탐색 — 모든 분기 경로를 시뮬레이션, 한 경로라도 증명 실패 시 전체 거부
  • 유한성 증명 — 프로그램이 반드시 종료함을 정적으로 보장, 무한 루프 불가
  • 레지스터·스택 상태 추적 — scalar / 포인터 타입과 값 범위 분석, 스택에 스필(spill)된 값의 타입까지 추적
  • 포인터 연산 경계 검증 — 맵 밖 접근·널 역참조·미초기화 읽기 거부
  • 레퍼런스 추적 — ringbuf reserve는 반드시 submit·discard로 종결, 커널 자원 누수 차단

한계와 진화

  • 검증 복잡도 상한 — 명령어 100만 개 탐색 한도
  • 루프: 초기엔 금지 → 커널 5.3+ bounded loop, bpf_loop() 헬퍼
  • 스택 512 B — 큰 버퍼는 맵을 스크래치 공간으로 사용
  • 보수적 판정 — 안전해도 증명이 안 되면 거부가 원칙
챕터 1에서 가장 중요한 장 — 시간을 써도 된다. 런타임 격리가 아니라 로드 타임 증명이라는 문장을 두 번 말해도 좋다. 레퍼런스 추적(reserve→submit)은 17~18장 링 버퍼에서 그대로 회수된다. 한계 패널: "안전해도 증명 안 되면 거부"가 보수성의 본질.
Where programs attach

프로그램 타입과 훅 — 커널 전역의 관측점

위(유저스페이스)에서 아래(NIC)로 훑기 — 깊이 갈수록 빠르고 원시적. sock_ops는 35장 NFM의 훅이라고 예고해두면 좋다. XDP는 패킷이 스택에 닿기도 전 — Cilium의 무기.
Shared state

Maps — 커널과 유저스페이스의 공유 상태

eBPF 프로그램은 상태를 가질 수 없습니다 — 상태는 전부 맵에, 커널 확장 기능은 헬퍼와 kfunc에 있습니다.

주요 맵 타입

  • HASH / ARRAY — 범용 키-값, LRU(Least Recently Used) 변형으로 자동 축출
  • PERCPU_* — CPU별 사본으로 락 없는 고속 집계
  • STACK_TRACE — bpf_get_stackid()가 채우는 호출 스택 저장소
  • RINGBUF — 커널 v5.8+ 이벤트 스트림의 표준

커널 기능의 창구

  • Helper Function — 고정 ABI의 안정 API (bpf_map_lookup_elem, bpf_ktime_get_ns …)
  • KFunc — 커널 함수를 직접 노출, 유연하지만 안정성 비보장
  • 헬퍼는 느리게 늘고, 신규 기능은 kfunc로 먼저 나오는 추세
  • 프로그램 타입별로 호출 가능한 헬퍼 집합이 다름 — Verifier가 강제
한 문장 요약: 상태는 맵에, 커널 기능은 helper/kfunc에. 프로그램 타입마다 호출 가능한 헬퍼 집합이 다르고 이것도 Verifier가 강제 — 11장과 연결. RINGBUF가 다음 다섯 장의 주제라고 브릿지.
Data structure primer

링 버퍼 — 고정 배열과 포인터 두 개로 만드는 무한 큐

eBPF가 발명한 구조가 아닙니다 — printk/dmesg 로그 · NIC RX/TX 링 · ftrace · perf · io_uring까지, 커널 도처에서 수십 년 검증된 자료구조입니다.

커널이 이 구조를 쓰는 이유

  • 인터럽트·스케줄러 같은 핫패스에선 malloc 불가 — 미리 잡은 슬롯에 쓰기만 한다
  • 메모리 사용량 상한이 설계 시점에 보장 — 폭주해도 버퍼 크기까지만
  • ns 단위 생산자와 ms 단위 소비자의 속도 분리 — 버퍼가 완충
  • 연속 메모리 한 덩어리 — mmap으로 유저스페이스와 공유해 복사 없이 읽는다
가득 참 정책이 용도를 가른다 — 로그(dmesg)는 오래된 것 덮어쓰기, 이벤트 파이프(perf·eBPF)는 새 이벤트 손실 + 카운트 Perf Buffer도 BPF Ring Buffer도 이 구조의 후예 — 무엇이 달라졌는가가 다음 네 장
자료구조 기초부터 까는 이유: 다음 네 장이 전부 이 구조 위의 변주라서. 포인터 두 개(P·C)와 고정 배열, 크기 2ᵏ 강제(& 연산), 가득 참 정책이 용도를 가른다 — 여기까지만 확실히 하면 뒤가 쉽다.
Legacy path — how it worked

기존 동작 방식 — CPU별 링에 조립 → 복사 → 즉시 알림

Perf Buffer는 앞 장의 링을 CPU마다 하나씩 둡니다 — BPF 프로그램은 자기 CPU의 링에만 쓰고, 소비자가 CPU 수만큼의 링을 따로 읽어 병합합니다.

링 자체는 앞 장 그대로 — 다른 것은 배치: CPU마다 따로 두고, 다 만든 레코드를 복사해 넣는다 이 그림에서 네 가지 대가가 그대로 파생 (다음 장)
Perf Buffer의 동작을 비난 없이 담담하게 — CPU마다 링 하나, 스택에서 조립 후 복사, 이벤트마다 알림. 그림의 세 CPU 불균형(넘침/제각각/텅 빔)을 손으로 가리키며. 판단은 다음 장으로 미룬다.

New path — how it works

새 동작 방식 — 예약 → 제자리 작성 → 커밋, 알림은 필요할 때만

링은 전역에 하나 — 모든 CPU가 reserve()로 자리를 먼저 확보하고, 그 자리에 직접 쓴 뒤 submit()으로 공개합니다. 복사가 사라지고, 순서는 예약 순서로 고정됩니다.

소비자는 BUSY 레코드 앞에서 멈춘다 — 커밋된 레코드만 예약 순서대로 공개 단일 링 · 예약 · 제자리 쓰기 · 적응형 알림 — 각각 무엇을 해소했는지는 다음 장
새 경로의 3단계 리듬 — reserve(자리 확보, 부족하면 즉시 실패) → 제자리 작성(복사 없음) → submit(공개). BUSY 비트와 이중 매핑(경계 걸친 레코드도 이어 읽기)은 그림에서 위치만 짚으면 충분.

MPSC

전역 단일 공유 버퍼

2단계 제로카피

reserve()가 공간을 먼저 확보 — 부족하면 즉시 실패해 대응 가능. 버퍼 메모리에 직접 쓰고 submit() — 중간 복사 제거.

ADAPTIVE

적응형 알림

소비자가 이미 처리 중이면 신호 억제, 지연될 때만 깨움 — 알림 비용을 데이터 양이 아닌 소비자 상태에 비례시킴.

DOUBLE MAP

가상 메모리 이중 매핑

같은 물리 페이지를 주소 공간에 두 번 연속 매핑 — 경계를 넘는 레코드도 wrap-around 처리 없이 연속 읽기.

ZERO WRAP COST
reserve는 반드시 submit·discard로 종결 — Verifier의 레퍼런스 추적이 강제(11장) 순서 꼬임·과다 할당·뒤늦은 유실·웨이크업 폭풍 — 전부 단일 버퍼 설계로 해소
한계 ↔ 메커니즘 1:1 매핑으로 정리 — 과다할당→MPSC, 복사→reserve/submit, 유실 감지→즉시 실패, 웨이크업 폭풍→적응형 알림. reserve는 반드시 submit/discard로 종결 — 11장 Verifier 레퍼런스 추적이 여기서 회수된다.

Compile once — run everywhere

CO-RE — 한 번 컴파일해서 어디서나 실행

문제의 근원: 커널 구조체 오프셋은 버전·설정마다 다릅니다. CO-RE는 오프셋을 런타임에 다시 계산합니다.

BTF dedup 5단계 — 문자열 → 비참조 타입 → struct/union 정준화 → 참조 타입 → 컴팩션, 수백 MB DWARF를 수 MB로 실측 — x86_64 pt_regs 오프셋(di=112 · si=104 · dx=96)을 로드 시점에 바이트코드로 패치 BCC(BPF Compiler Collection)의 런타임 컴파일(clang 내장) 없이 경량 정적 바이너리 배포
문제 제기부터 — 커널 구조체 오프셋은 버전마다 다르다. 컴파일 타임(재배치 레코드) → 런타임(커널 BTF + libbpf 패치) 순으로. pt_regs 실측 칩(di=112…)이 "진짜 바이트코드를 고친다"는 증거.

Case study № 1

메모리 누수 추적 — 집계는 전부 커널 안에서

동작 원리

  • 할당 경로에 프로브 — 유저 malloc·calloc·realloc·mmap은 uprobe, 커널 kmalloc은 kprobe → 주소 → (스택 ID · 크기 · 시각)을 맵에 기록
  • 해제 시 해당 엔트리 삭제 — 오래 남은 엔트리 = 누수 후보
  • bpf_get_stackid()가 호출 스택을 STACK_TRACE 맵에 저장
  • 유저스페이스는 주기적으로 맵만 읽음 — 이벤트 스트리밍 없음, 오버헤드 최소
# PID 1234의 미해제 할당을 10초 간격으로 추적 $ memleak -p 1234 --interval 10 [13:42:01] Top 10 stacks with outstanding allocations: 524288 bytes in 128 allocations from stack malloc+0x1f grow_request_buffer+0x42 handle_connection+0x8d start_thread+0xd9 # --older: 60초 이상 미해제 '진성 누수'만 · -p 생략 시 커널 누수 추적 $ memleak -p 1234 --older 60000
Valgrind와 달리 재기동 불필요 — 실행 중인 프로세스에 동적 부착, CPU 에뮬레이션 없이 커널 내 집계 uprobe의 비용 — int3 브레이크포인트 트랩으로 매 호출마다 커널 왕복, 고빈도 malloc에선 트랩 자체가 병목 우회로는 커널 진입 제거 — bpftime이 프로브를 유저스페이스 인라인 훅으로 실행, 약 10배 단축 (22장)
케이스 스터디 시작 — Valgrind와의 대비(재기동 불필요, 실행 중 프로세스에 부착)가 첫 반응 포인트. 집계가 전부 커널 안 = 오버헤드 최소. uprobe int3 트랩 비용 → bpftime(22장) 회수로 마무리.
Case study № 2

Off-CPU 분석 — CPU 밖의 시간을 본다

왜 필요한가

  • On-CPU 프로파일은 절반만 본다 — 대기 시간은 샘플에 안 잡힘
  • 락 경합·디스크 I/O·페이지 폴트가 지연의 주범인 경우가 많음
  • 스위치 아웃 시각 → 복귀 시 Δt를 스택별로 커널 내 집계
  • 결과물은 Off-CPU Flame Graph — 어떤 스택이 얼마나 기다렸나
질문으로 열기 — "프로파일러에 안 잡히는 지연, 어디서 찾습니까?" On-CPU 프로파일은 절반만 본다. finish_task_switch() 하나로 모든 컨텍스트 스위치를 관측한다는 게 이 장의 감탄 포인트.

  • CPU 사용률 그래프는 limit에 붙어 평평 — 일하는 중인지 목이 졸린 중인지 구분 불가
  • cAdvisor 스로틀 카운터는 횟수·총량만 — 어느 코드 경로가 얼마나 늦었는지 없음
  • runqlat 스파이크 + Off-CPU 스택(27장)에 블로킹 흔적 없음(io_schedule·futex_wait 부재) → I/O도 락도 아닌 스로틀링으로 확정
  • 두 도구의 교차 판독이 limits 재산정의 정량 근거가 된다
관측 조합진단처방
runqlat 스파이크 + 스택에 블로킹 흔적 없음 — 깨어 있는데 못 뛴다CFS 스로틀링 — CPU 할당 부족limits.cpu 상향이 유효
runqlat 정상 + 스택 끝에 io_schedule·futex_wait — 스스로 잠들었다I/O·락 병목 — CPU와 무관limits 상향 무효 — 스토리지·락 설계를 개선
증상부터 — CPU 그래프는 평평한데 지연이 튄다. runqlat 스파이크 + Off-CPU 스택에 블로킹 흔적 없음 = 스로틀링 확정이라는 교차 판독 논리가 핵심. 아래 표의 두 행이 "limits 상향이 유효한가"를 가르는 처방 분기.
Runtime security № 1

Falco — 관측은 하지만, 막지는 못한다

탐지는 강력 — 방대한 룰셋과 생태계 그러나 차단은 사후 대응 — kill은 이미 늦은 시점
그림의 파이프라인을 왼→오로 따라간 뒤 반전 — 판정이 도착했을 때 시스템 콜은 이미 끝나 있다. TOCTOU 한 줄 설명. Falco 폄하가 아니라 구조적 위치의 문제임을 분명히(탐지 자체는 강력).
Runtime security № 2

Tetragon — 커널 안에서 판단하고, 그 자리에서 차단한다

Falco = 사후 탐지 (detection) Tetragon = 동기 실행 차단 (enforcement) Kubernetes-aware — TracingPolicy CRD(Custom Resource Definition)로 Pod·네임스페이스 단위 정책 다음 단계는 상관 분석 — 커널 eBPF 데이터를 클라우드 API·앱 시그널과 엮어 전체 공격 스토리 재구성 (ARMO CADR · Cloud Application Detection & Response)
대비가 전부 — Falco는 비동기 사후 탐지, Tetragon은 LSM 훅에서 동기 판정, 같은 커널 컨텍스트에서 차단까지 완결. -EPERM vs SIGKILL 두 차단 수단. TracingPolicy CRD로 K8s 네이티브라는 점도.

eBPF on EKS № 3

Cilium ENI 모드 — 오버레이 없는 eBPF 데이터패스

무엇이 달라지나

  • kube-proxy replacement — iptables O(n) 체인 순회 → eBPF 해시맵 O(1) 조회, 서비스 수가 늘어도 룩업 비용 일정
  • ENI IPAM(IP Address Management) — Pod에 VPC IP 직접 부여, 오버레이 오버헤드 제거
  • Hubble — 동일 데이터패스에서 플로우 관측을 덤으로 획득
  • Gateway API·mTLS·Bandwidth Manager 등 메시 기능 흡수
Cilium ENI 모드의 3대 변화 — kube-proxy 제거(iptables O(n) → eBPF O(1)), Pod에 VPC IP 직접 부여(오버레이 없음), Hubble 관측 덤. 빨간 점선 박스(kube-proxy 소멸)를 가리키며.

Take these home

커널을 읽을 수 있으면, 클러스터가 보인다

1

Verifier가 계약이다

eBPF의 안전은 런타임 격리가 아니라 로드 타임 증명. 512 B 스택·bounded loop 같은 제약은 그 증명의 대가다.

2

CO-RE가 배포를 바꿨다

BTF 재배치로 커널별 재컴파일이 사라졌다. libbpf 정적 바이너리가 프로덕션 표준 — BCC는 실험용으로.

3

EKS에선 이미 기본기

NetworkPolicy 에이전트·Cilium·NFM 모두 eBPF 위에서 돌고, NFM은 소스까지 공개되어 있다. 이해하는 순간 디버깅 계층이 하나 더 생긴다.

세 챕터를 관통하는 한 문장 — eBPF는 커널을 고치지 않고 커널의 동작을 바꾸는, 검증된 프로그래밍 계층입니다.

세 가지를 손가락으로 꼽으며 — Verifier가 계약, CO-RE가 배포를 바꿈, EKS에선 이미 기본기. 관통 문장을 천천히: 커널을 고치지 않고 커널의 동작을 바꾸는, 검증된 프로그래밍 계층.
