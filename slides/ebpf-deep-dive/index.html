The problem

커널 확장의 두 가지 길

커널에 코드를 넣는 전통적 방법은 커널 모듈 — 강력하지만 커널과 운명을 함께합니다.

커널 모듈 (LKM)

  • 버그 하나 = 커널 패닉, 시스템 전체 다운
  • 커널 버전마다 재컴파일·재검증 — ABI 비보장
  • 서명·배포·감사 부담, 보안팀의 승인 장벽
  • 메모리 접근 무제한 — 격리 장치 없음

eBPF 프로그램

  • Verifier가 로드 전에 안전성을 증명 — 크래시 불가
  • 레지스터 기반 샌드박스 VM에서 실행, JIT로 네이티브 성능
  • CO-RE로 커널 버전 간 이식 — 재컴파일 없음
  • 재부팅·모듈 로드 없이 즉시 attach / detach
"안전하게 커널을 프로그래밍한다" — 이 설계의 원형은 30년 전에 이미 있었다
Prior art — 1992

해답의 원형 — tcpdump의 패킷 필터

tcpdump는 필터를 유저스페이스에서 돌리지 않습니다 — 표현식을 바이트코드로 컴파일해 커널 안으로 내려보내고, 매치된 패킷만 돌려받습니다.

eBPF가 물려받은 세 가지

  • 코드를 데이터가 있는 곳으로 — 패킷 전체를 복사해 거르지 않고, 필터를 커널에 주입
  • 검증 가능한 제한 명령어 — 임의 기계어가 아닌 바이트코드
  • 커널 수정 없는 프로그래밍 — 커널 내 엔진이 실행
  • eBPF는 이 원리를 그대로 두고 엔진만 재설계 — 'e'는 extended
cBPF — 레지스터 2개 · 32-bit · 소켓 필터 전용 → eBPF — 11개 · 64-bit · 커널 전역 지금도 tcpdump 필터는 커널에서 eBPF로 변환되어 실행된다
Evolution — 1992 to today

패킷 필터에서 범용 커널 VM까지

도입 배경: 커널 기능 하나가 메인라인을 거쳐 배포판에 닿기까지 수년 — 컨테이너 시대의 네트워킹·관측·보안 요구를 커널 릴리스 주기가 따라가지 못했습니다.

커널 릴리스 주기 ≫ 인프라 요구의 변화 속도 모듈은 위험하고, 커널 포크는 유지비용이 크다 선행 기술 DTrace는 CDDL 라이선스 — GPL 커널에 통합 불가, 독자 노선을 강제한 배경 해법 — 커널 안에 안전한 프로그래밍 계층을 내장한다

eBPF VM은 하드웨어 가상화가 아니라 커널이 정의한 명령어 실행 모델입니다 — 바이트코드라는 중간 표현이 있어야 Verifier가 정적 분석을 할 수 있습니다.

The gatekeeper

Verifier — 실행 전에 안전을 증명한다

런타임 격리가 아니라 로드 타임 정적 검증. 증명에 실패하면 커널은 프로그램을 받지 않습니다.

무엇을 검사하는가

  • CFG 전수 탐색 — 모든 분기 경로를 시뮬레이션, 한 경로라도 증명 실패 시 전체 거부
  • 유한성 증명 — 프로그램이 반드시 종료함을 정적으로 보장, 무한 루프 불가
  • 레지스터 상태 추적 — scalar / 포인터 타입과 값 범위 분석
  • 포인터 연산 경계 검증 — 맵 밖 접근·널 역참조·미초기화 읽기 거부
  • 레퍼런스 추적 — ringbuf reserve는 반드시 submit·discard로 종결, 커널 자원 누수 차단

한계와 진화

  • 검증 복잡도 상한 — 명령어 100만 개 탐색 한도
  • 루프: 초기엔 금지 → 커널 5.3+ bounded loop, bpf_loop() 헬퍼
  • 스택 512 B — 큰 버퍼는 맵을 스크래치 공간으로 사용
  • 보수적 판정 — 안전해도 증명이 안 되면 거부가 원칙

Shared state

Maps — 커널과 유저스페이스의 공유 상태

eBPF 프로그램은 상태를 가질 수 없습니다 — 상태는 전부 맵에, 커널 확장 기능은 헬퍼와 kfunc에 있습니다.

주요 맵 타입

  • HASH / ARRAY — 범용 키-값, LRU 변형으로 자동 축출
  • PERCPU_* — CPU별 사본으로 락 없는 고속 집계
  • STACK_TRACE — bpf_get_stackid()가 채우는 호출 스택 저장소
  • RINGBUF — 커널 v5.8+ 이벤트 스트림의 표준

커널 기능의 창구

  • Helper Function — 고정 ABI의 안정 API (bpf_map_lookup_elem, bpf_ktime_get_ns …)
  • KFunc — 커널 함수를 직접 노출, 유연하지만 안정성 비보장
  • 헬퍼는 느리게 늘고, 신규 기능은 kfunc로 먼저 나오는 추세
  • 프로그램 타입별로 호출 가능한 헬퍼 집합이 다름 — Verifier가 강제
Legacy — perf buffer

CO-RE — 한 번 컴파일해서 어디서나 실행

Case study № 2

Off-CPU 분석 — CPU 밖의 시간을 본다

왜 필요한가

  • On-CPU 프로파일은 절반만 본다 — 대기 시간은 샘플에 안 잡힘
  • 락 경합·디스크 I/O·페이지 폴트가 지연의 주범인 경우가 많음
  • 스위치 아웃 시각 → 복귀 시 Δt를 스택별로 커널 내 집계
  • 결과물은 Off-CPU Flame Graph — 어떤 스택이 얼마나 기다렸나

Take these home

커널을 읽을 수 있으면, 클러스터가 보인다

1

Verifier가 계약이다

eBPF의 안전은 런타임 격리가 아니라 로드 타임 증명. 512 B 스택·bounded loop 같은 제약은 그 증명의 대가다.

2

CO-RE가 배포를 바꿨다

BTF 재배치로 커널별 재컴파일이 사라졌다. libbpf 정적 바이너리가 프로덕션 표준 — BCC는 실험용으로.

3

EKS에선 이미 기본기

NetworkPolicy 에이전트·Cilium·NFM 모두 eBPF 위에서 돌고, NFM은 소스까지 공개되어 있다. 이해하는 순간 디버깅 계층이 하나 더 생긴다.

세 챕터를 관통하는 한 문장 — eBPF는 커널을 고치지 않고 커널의 동작을 바꾸는, 검증된 프로그래밍 계층입니다.
